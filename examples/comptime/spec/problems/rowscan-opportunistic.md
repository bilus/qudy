# Reading database rows into structs (opportunistic)

## Problem

A library exports a generic function that reads the current row of a
`*sql.Rows` into a struct. Each field with a `db` tag takes one column:

```go
// Package rowscan reads database rows into structs.
package rowscan

// Scanner is the part of *sql.Rows that Scan uses.
type Scanner interface{ Scan(dest ...any) error }

// Scan reads the current row into a new T. Each field with a db tag takes one
// column, in field order.
func Scan[T any](rows Scanner) (T, error) {
	var x T
	v := comptime.ValueOf(&x)
	var dest []any
	for f := range comptime.TypeFor[T]().Fields() {
		if f.Tag.Get("db") != "" {
			dest = append(dest, v.Field(f).Addr().Interface())
		}
	}
	err := rows.Scan(dest...)
	return x, err
}
```

Another package calls it on its own type:

```go
type User struct {
	ID    int64  `db:"id"`
	Name  string `db:"name"`
	Email string `db:"email"`
	Notes string // not a column
}

func readUsers(rows rowSource) ([]User, error) {
	var users []User
	for rows.Next() {
		u, err := rowscan.Scan[User](rows)
		if err != nil {
			return nil, err
		}
		users = append(users, u)
	}
	return users, rows.Err()
}
```

On every row, `Scan` walks the fields of `User` with reflection, reads their
tags, and builds the slice of destinations. The type, and so the fields and
tags, are the same for every row: only the column values change.

The goals:
- The caller's package builds and runs without `go-comptime`.
- With `go-comptime`, the call does no reflection.
- `rowscan` is an ordinary library. Callers in other packages, with types that
  `rowscan` has never seen, use it the same way.

## Solution

> **Opportunistic, but beyond the first version.** The solution needs
> specialization, which R1 to R18 do not cover. R6 replaces only the
> initialization expressions of tagged variables, and R4 does not cover the
> positions of an added function. A conforming first version writes no
> comptime file for this package.

The `comptime` package runs on `reflect`, so without `go-comptime` the code
above runs as it is. With `go-comptime`, the call is specialized in the
caller's package, not in `rowscan`:

- The tool writes a copy of `Scan` for `User` into the caller's comptime file,
  and rewrites the call to use it.
- The copy may use only names that `rowscan` exports, because it lives in
  another package.
- `rowscan` itself needs no comptime file. Any package, with any type, gets its
  own copy.

The comptime file `app/.comptime/users.go` is the source with one call
replaced and one function added:

```go
// Code generated by go-comptime from users.go. DO NOT EDIT.

//line ../users.go:1:1
package app
…
		u, err := /*line ../users.go:38:13*/scanUser(rows)/*line ../users.go:38:37*/
…

// scanUser is rowscan.Scan specialized for User.
//line ../users.go:38:13
func scanUser(rows rowscan.Scanner) (User, error) {
/*line ../users.go:38:13*/	var x User
/*line ../users.go:38:13*/	err := rows.Scan(&x.ID, &x.Name, &x.Email)
/*line ../users.go:38:13*/	return x, err
/*line ../users.go:38:13*/}
```

Each line of the added function points at the call, so an error or a panic in
it reports the line the user wrote.

## Evidence

- `go vet` and `go test` pass with and without the overlay.
- `readUsers` over two fake rows: 1525 to 1581 ns and 19 allocations without
  the overlay; 256 ns and 7 allocations with it.
- Errors planted in the comptime file reported `app/users.go:38:34` and
  `app/users.go:42:28`.
- Measured separately, for one call: reflection about 450 ns, dispatch through
  a registry of generated functions about 100 ns, a direct copy about 65 ns.

## Open points

- The spec owner proposes to keep this case as a target for the version with
  specialization, rather than as a conformance case of the first version.
- How many copies one function may get (open question 4 of the strict
  proposal applies here too).
