# A base64 encoding from a literal alphabet

## Problem

A package defines base64 encodings the way `encoding/base64` does: a
constructor takes a 64-character alphabet and a padding character, checks
them, and builds a 256-entry decode table.

```go
type Encoding struct {
	encode  string
	decode  [256]byte // the value of each byte of the alphabet, 0xFF for any other byte
	padChar int32
}

// NoPadding asks NewEncoding for an encoding without padding.
const NoPadding int32 = -1

// NewEncoding returns the encoding with the alphabet and the padding
// character, or NoPadding. It panics on an alphabet that is not 64 distinct
// bytes, or that holds the padding character, '\r' or '\n'.
func NewEncoding(alphabet string, padding int32) Encoding { … }

var URLEncoding = NewEncoding("ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_", '=')
var RawURLEncoding = NewEncoding("ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_", NoPadding)
```

The two package variables are built from a string literal and an int literal.
Their tables are filled at program start, and a mistake in an alphabet, such
as a repeated byte, shows up only as a panic at program start:

```
panic: b64: the alphabet repeats A

goroutine 1 [running]:
example.com/b64.NewEncoding({_, _}, _)
	…/encoding.go:40 +0x1cc
example.com/b64.init()
	…/encoding.go:55 +0xbb
```

The goal: build both encodings at build time, so that the table is a literal
in the build and a bad alphabet stops the build. `NewEncoding` must stay a
run-time function that callers can use with their own alphabets.

## Solution

This is opportunistic and within the first version: R14 tags the function,
R2 tags the variables, and R6 replaces each tagged initializer with its value.

```go
//qudy:comptime
func NewEncoding(alphabet string, padding int32) Encoding { … }

//qudy:comptime
var URLEncoding = NewEncoding("ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_", '=')

//qudy:comptime
var RawURLEncoding = NewEncoding("ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_", NoPadding)
```

The comptime file `.comptime/encoding.go` is the source with two initializers
replaced, each on its own line, between line directives (R4):

```go
// Code generated by go-comptime from encoding.go. DO NOT EDIT.
//line ../encoding.go:1:1
…
var URLEncoding = /*line ../encoding.go:50:19*/Encoding{encode: "ABC…-_", decode: [256]byte{0xff, …, 0x3e, …}, padChar: 61}/*line ../encoding.go:50:103*/
…
var RawURLEncoding = /*line ../encoding.go:55:22*/Encoding{encode: "ABC…-_", decode: [256]byte{…}, padChar: -1}/*line ../encoding.go:55:106*/
```

- The table is computed once, at build time, and is visible in the comptime
  file.
- A bad alphabet panics during evaluation. R1 makes that an error at the call,
  `encoding.go:55:22`, instead of a panic at program start.
- `NewEncoding` stays in the binary, so callers can still build encodings with
  other alphabets at run time.

The run-time gain is only at program start: a few hundred nanoseconds, once.
The value is that the mistake is caught at build time.

## Why there is no strict version

A strict version would remove `NewEncoding` from the binary, so callers could
no longer build their own encodings. It would gain nothing over the
opportunistic version, which already moves the table and the checks to build
time.

## Evidence

- `go vet` and `go test` pass both with and without the overlay.
- The test compares both encodings with `base64.URLEncoding` and
  `base64.RawURLEncoding` on 200 random inputs, round-trips the decoding, and
  checks that `+` and `/` are rejected.
- `NewEncoding` panics on an alphabet that is too short, that repeats a byte,
  or that holds the padding character.

## Open points

- A type error planted inside the literal reported `./encoding.go:50:1668`, a
  column far past the end of that 100-character source line. A directive
  before a literal sets only where the literal starts, so positions inside a
  long literal run on. The spec should either say that such columns are
  accepted, or require the tool to wrap long literals.
- The exact text of the R1 error for this case is unverified, because no tool
  produces it yet.
