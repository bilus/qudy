# A named type whose definition is computed

## Problem

[vector.md](vector.md) describes a type with a function, `vector(3)`. A
program wants a named type with that definition, plus methods on it, as if
it had written:

```go
type point [3]int64

func (p point) Norm2() int64 { return p[0]*p[0] + p[1]*p[1] + p[2]*p[2] }
```

Go cannot compute a type in a type declaration. `var point = vector(3)` makes
a variable that holds a description of a type, not a type, and so it cannot
have methods or appear as a type in other code.

The other goals:
- The source should hold all the pieces, even if gopls complains about some
  of them. There are no stub files.
- gopls should keep working on the source as far as it can.

## Solution

> **Strict comptime, not opportunistic.** The source does not build without
> `go-comptime`; the generated file does. This follows
> [the strict proposal](../proposal-alternative-strict-comptime.md), which is
> not approved.

The name gets its type in two lines: a placeholder declaration, and a
`Reify` call that says what to compute. The name follows Zig, where `@Type`
reified a description of a type into a type.

```go
// geo.go
//go:build comptime

package geo

import "example.com/geo/comptime"

// vector describes an array of n int64 coordinates.
func vector(n int) comptime.Type {
	return comptime.ArrayOf(n, comptime.TypeFor[int64]())
}

// point is a point in three dimensions.
type point struct{ comptime.Reified }

var _ = comptime.Reify[point](vector(3))

// newPoint returns the point at x, y, z.
func newPoint(x, y, z int64) point {
	var p point
	for i, c := range []int64{x, y, z} {
		p.Index(i).SetInt(c)
	}
	return p
}

// Norm2 returns the square of the point's distance from the origin.
func (p point) Norm2() int64 {
	var s int64
	for i := range p.Len() {
		c := p.Index(i).Int()
		s += c * c
	}
	return s
}
```

The `//go:generate go-comptime` line goes in a file without the tag,
`doc.go`, so that `go generate` finds it in a normal build. `go-comptime`
writes `geo_gen.go`, which is committed:

```go
// Code generated by go-comptime from geo.go. DO NOT EDIT.

//go:build !comptime

package geo

// point is a point in three dimensions.
//
//line geo.go:13:6
type point [3]int64

// newPoint returns the point at x, y, z.
//
//line geo.go:18:1
func newPoint(x, y, z int64) point {
	var p point
//line geo.go:21:3
	p[0], p[1], p[2] = x, y, z
//line geo.go:23:2
	return p
}

// Norm2 returns the square of the point's distance from the origin.
//
//line geo.go:27:1
func (p point) Norm2() int64 {
//line geo.go:31:3
	return p[0]*p[0] + p[1]*p[1] + p[2]*p[2]
}
```

- Embedding `comptime.Reified` gives the placeholder the methods of `Value`,
  such as `Index` and `Len`. Code that reads `point` through them
  type-checks in gopls.
- The loops over a length known at build time are unrolled.
- The line directives name `geo.go` by its base name, because both files share
  a directory. On Go 1.27, a relative name resolves against the directory of
  the file that holds the directive. An absolute path would put the machine's
  directories into committed files.
- With `"buildFlags": ["-tags=comptime"]`, gopls checks the comptime source
  and skips the generated file. Without the `!comptime` tag, gopls would report
  every declaration as redeclared.

## Evidence

- The package builds and passes `go vet` with and without `-tags comptime`.
  The test of the generated code passes.
- Without `//go:build !comptime` in `geo_gen.go`, `gopls check` with the
  comptime tag reports each declaration as redeclared.
- Without the tag, `gopls check` reports nothing for the comptime source, not
  even a real error.
- `geo_gen.go` is hand-written; no tool produced it.

## Open points

- The name of the build tag: `comptime`, or one less likely to collide with
  the tags of dependencies.
- Whether `go-comptime -w` should write the computed definition back into the
  placeholder, so that gopls stops reporting computed members.
